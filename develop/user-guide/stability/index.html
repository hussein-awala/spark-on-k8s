    Interface stability and 1.0¶

    This page classifies the public surfaces of the current source and states what each level promises. The support boundaries define what the project owns and how a documented contract is retired; this page applies that policy surface by surface. Use the documentation for your installed release: some surfaces listed here do not exist in older releases.

    Stability levels¶

    Level What you can rely on
    Stable A documented contract you can build automation on. A patch release does not change it incompatibly. An incompatible change in a minor release follows the deprecation process: a release-note notice, normally a usable compatibility path for at least one published release, a deprecation register entry and migration steps. A security or correctness fix can break a contract sooner; its release notes state the reason and the operational consequence prominently.
    Experimental Available for evaluation while its design settles. It can change or be removed in any release. Release notes record the change, without a deprecation period.
    Internal An implementation detail, even when it is importable, visible in the browser or reachable over HTTP. It can change in any release without notice.

    A surface that is neither documented in a guide nor listed on this page is Internal. Human-readable output is never a contract: progress and error messages, --help text, log formatting and the console's layout can change in any release. Automation uses the versioned JSON results and exit codes instead.

    Stable behavior includes the lifecycle rules stated across the guides. An uncertain status is not reported as absence. A submission receipt identifies a run; it does not establish that the workload or its data writes succeeded. An observation timeout does not cancel the application; the Airflow operator's startup timeout is the documented exception that deletes a Pending driver. A shared operator token is not tenant isolation.

    Versioned documents¶

    Several Stable contracts carry a version marker: schema_version in JSON results and files, apiVersion: spark-on-k8s/v1 in job files and /v1 in HTTP paths. Within one marker, changes are additive, such as a new field in a result. Consumers check the marker, ignore unknown fields and do not depend on key order or messages. A change that existing consumers cannot tolerate, such as removing or renaming a field or changing its type or meaning, uses a new marker and follows the deprecation process.

    A release can add optional job-file fields, and existing job files keep working after an upgrade. Job files reject unknown settings, so a file that uses a new field needs a release that knows it.

    Versioning¶

    The Python package and its API image share one version. The Helm chart and the dbt adapter have independent versions; see packages and release order.

    Before 1.0, a patch release (0.Y.Z) contains fixes and does not change a Stable surface incompatibly, apart from the security and correctness exception. A minor release (0.Y.0) adds features and can make an incompatible change to a Stable surface only through the deprecation process.

    From 1.0, Stable surfaces follow Semantic Versioning: an incompatible change needs a new major version and a deprecation notice in an earlier minor release, minor releases add compatible features and deprecations, and patch releases contain fixes. The security and correctness exception remains, stated prominently in release notes. Experimental and Internal surfaces keep their levels.

    Criteria for 1.0¶

    The spark-on-k8s package and API image move to 1.0.0 when every criterion below holds. Each names evidence a reviewer can check. The Helm chart and the dbt adapter decide their own 1.0 separately. 1.0 is a statement about interface stability; it does not add a support period, a response time or a certification.

    1. Classified surfaces. Every public surface appears on this page, each Stable row links to its canonical guide or reference page, and no Stable surface depends on an Experimental one. Experimental surfaces stay outside the 1.0 promise unless they first become Stable. Evidence: this page and a strict documentation build.
    2. Contract tests. Each versioned document and each documented exit code has a regression test for its marker, required fields and codes, so an incompatible change fails CI. Evidence: the test paths, listed in the 1.0 release PR.
    3. Two releases without breaks. Every versioned Stable contract has shipped unchanged, apart from additive changes, in at least two consecutive published minor releases. Evidence: release notes for those releases.
    4. No pending removals. The deprecation register has no entry awaiting removal, so 1.0 starts without scheduled breaking changes. Evidence: the register.
    5. Legacy paths decided. The register or this page records whether each legacy path is retained or retired: the Airflow 2.11 compatibility profile, the text-only app kill, app delete and app logs commands, and the unversioned application routes under /apps and /app. Evidence: the recorded decisions.
    6. Release process exercised. At least two releases were published through the tag-triggered workflow with exact-commit eligibility, a retained release record of package hashes, image digests and chart version, and a GitHub release body extracted from its release-notes file. Evidence: the release records.
    7. Qualified deployment. The 1.0 candidate's API image and matching chart version pass a staging smoke test and are recorded as a cluster-qualified combination. Evidence: the release record.
    8. Named runtime matrix. The installation and compatibility guides name the supported Python, Spark, Airflow and Kubernetes versions for 1.0, and each has a CI job that passes on the release commit. Evidence: the release eligibility record.
    9. Security process. Private vulnerability reporting is enabled, the security policy states which release lines receive fixes, including the previous major line after a later major release, and no accepted advisory for the release line is unresolved. Evidence: the repository's Security tab.
